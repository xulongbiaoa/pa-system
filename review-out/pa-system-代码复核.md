复核对象：`https://github.com/xulongbiaoa/pa-system`，clone 至 `pa-system/`，288 文件，VERSION `0.1.0`。
复核方式：通读五层代码 + 跑全量测试 + 用数据集真实未来段复算两笔放行单 + 针对可疑规则构造反例实测。

## 0. 结论先说

**规则文档是自洽的，代码在四处与文档不一致，其中两处会让红线形同虚设。** 感知层和知识层的质量明显高于裁决层；最该动的不是特征，是 `gate/risk_rules.py`。

41 个测试全过，但测试没覆盖这四处——因为测试用例是按代码行为写的，不是按 core 写的。

## 2. 问题清单

### P0-1　单笔风险上限：代码 1.5%，core 写 1%

`gate/risk_rules.py:12` `RISK_FRAC_MAX = 0.015`，而 `knowledge/core.md:21` 红线 3 是「单笔风险 1%」。core 开头写明「本文件冲突时以本文件为准」，所以代码这边是错的，来源应是 `knowledge/archive/architecture-proposal-20261030.md:148` 的「1% 到 1.5%」——方案原文的口径没跟着冻结口径收窄。

实测：

```
risk_frac=0.010 -> pass []
risk_frac=0.015 -> pass []      ← 按 core 应该 reject
```

影响：单笔风险被放宽 50%，所有回放的 R 序列分母都偏大，跨批次比较不可信。

修法：`RISK_FRAC_MAX = 0.01`，并补一条测试「1.01% 必须 reject」。

---

### P0-2　净 RR 门槛按末级目标算，回放却按首目标结算

`gate/risk_rules.py:38` `rr_main = rr_by_target[-1]`，`eval/pilot_run.py:83` `plan["targets"][0]`。

裁决用最远的目标判断够不够 1.5，结算用最近的目标算 R。这是**两个不同的目标**，中间那段就是漏洞：只要在计划里多写一个远目标，任何烂计划都能过门槛。

实测（entry 100 / stop 101.37 / targets [99.2, 95.0]）：

```
首目标净RR = 0.48（回放按此结算） | 末级净RR = 3.34（H1 实际用此）
裁决 = pass | 硬规则 = []
```

一笔实际最好只能拿 0.48R 的计划，裁决层放行了。这正是 core 交易者等式里明令禁止的「目标改近」的反向利用——不用改近，加一个远目标就行。

`judge/schema.json` 里 `targets` 只有 `minItems: 1`，没有顺序约束，等于把这个口子敞开。

修法（两条一起）：
1. H1 改用 `targets[0]`，与回放结算口径对齐；
2. schema/validate 增加单调性校验：`targets` 必须按有利方向严格递增（空头递减），且每级都要能算出 RR 明细留档。

### P0-3　H4 没有模式开关，与红线 4 定版不符

core 红线 4 已定版：入场截止只约束 trainer 局内。但 `risk_rules.py:62` 仍是无条件硬规则：

```python
if bars_left < CUTOFF_LEFT:
    hard.append({"rule": "H4", ...})
```

`adjudicate()` 没有 `mode` 参数，标注/试点/trainer 走同一条路。现在之所以不误杀，纯属数据形状碰巧——`pilot_run.py:71` 传的是 `len(seg["bars"]) - 180 = 300`，300 ≥ 10 所以不触发。**只要将来评估窗短于 10 根（比如做 5 根前向的短窗试验），全量样本会被静默否掉，而且日志里只会看到一片 H4，看不出是口径错误。**

实测：

```
bars_left=5 -> reject ['H2', 'H4']
```

修法：`adjudicate(..., mode="annotation"|"trainer")`，H4 只在 `mode=="trainer"` 时判；`bars_left` 的语义也要改名为 `bars_to_window_end`，避免和「未来窗长度」混用（现在两个含义在同一变量名上打架）。

### P1-4　H6 模式停牌在管线里是死的

`risk_rules.py:75` 用 `(plan["setup"], plan["context"])` 查台账，而 `pilot_run.py:69` 把 `context` 塞成了假设正文：

```python
"context": (j["hypotheses"][0]["statement"] if ... )
```

自由文本永远匹配不上 `("A2","下降")` 这种键。而且 `pilot_run` 调 `adjudicate` 时**根本没传 `ledger`**，`ledger=None` 直接跳过 H6。

实测：

```
H6（context=假设正文）-> pass []
H6（context=语境标签）-> reject ['H6']
```

修法：`context` 从判断 JSON 的语境枚举字段取（不要用 statement），并把 `ledger` 从回放结果累计后传进来。现在这条规则等于没实现。

### P1-5　「压整数位」检查只对整数价标的有效

`risk_rules.py:56`：

```python
if seg_avg and abs(stop - round(stop)) < 0.02 * seg_avg:
```

`round()` 对 11.80 返回 11（差 0.80），对 0.87 返回 1（差 0.13），永远大于 `0.02*seg_avg`，所以对小数价标的几乎不可能触发；对 BTC 这种整数价（25588.0）才正常。

实测：

```
stop=11.8   命中H2整数位=False   ← 11.80 是典型整数位，没抓到
stop=0.87   命中H2整数位=False
stop=25588  命中H2整数位=True
```

影响：这条红线在 15m 山寨币上形同虚设，而这批样本大半是 15m 山寨币。

修法：按标的的最小报价单位（tick）或按 `10^k` 网格判定，例如把 stop 归一到 `seg_avg_range` 量级的整档再比；不要用 Python 的 `round()`。

### P1-6　金标准集没有任何代码引用

`knowledge/gold/INDEX.md` 写着「此后任何知识/提示/感知改动须全量重跑本集，通过率不得下降」，但全仓 `grep -rn "gold" --include=*.py` **零命中**：没有 loader、没有回归测试、没有 CI 钩子。

这等于把最重要的一条纪律写在了文档里，靠人记。30 段冻结集的唯一价值就是当回归基线，不被代码引用就只是一堆 JSON。

### P1-7　基线口径与系统不一致，对照不成立

`eval/baselines.py:19` `WARM, END = 30, 170  # 末尾留 10 根截止` —— 把**已废止的旧截止**写死在基线里。系统按新口径可以在决策点入场，基线却被禁止在 170–179 入场，两者评估的是不同的入场全集。

另外基线用 `simulate_trade(bars[i+1:], ...)`，吃到段末（最长 449 根）；系统固定 300 根。**生命周期都不一样，胜率和 R 不可比。**

这解释了 changelog 里「简单基线 31 段只触发 2 笔」——不一定只是形态稀少，基线自己的截止线把它卡住了。

修法：基线改为在决策点（bar 180）入场、生命周期同为 300 根，与系统同口径；旧截止从基线里删掉。

### P1-8　C1（MTR）在提示里永远不可达

`judge/prompt_builder.py:21` `route_cards` 只按 `trend.label` 三分类，返回 `A1/A2 + B1 + B3` 或 `B3`。而 `router.md` 有第四个分支「反转候选 → MTR 卡」，代码里没有任何路径能返回 `C1-m2b...`（实际文件名是 `C1-mtr`）。

B2 不可达可以接受（卡片原文写明「回踩成第二腿即并入 A1/A2」），但 C1 是真缺口：老趋势+两腿衰竭+TBTL 这个语境在机器路由里不存在，6 张卡实际只有 4 张能用。

修法：`route_cards` 增加反转候选判定（`trend_age` 大 + `pullback.expired` + 要塞测试次数），命中时返回 C1。

### P2-9　`major` 摆动窗口 5 根，是标签噪声与滞后的根因

`perception/config.json` `swing_window_major: 5`。±5 根在 15m 上只有 75 分钟，把「大级别摆动」定义成了小级别。后果有两层：

1. `trend_state()` 只取**最后 2 个高点和 2 个低点**比大小，等价于「最近 10–20 根的方向」，不是趋势。这正是我上一轮点出的 5 段标签冲突（ds18/ds06/ds19/ds21/WIF-15m）的机制来源，不是偶发。
2. `swings.py:13` `for i in range(window, n - window)` 让最近 `window` 根**永远不可能成为摆动**，所以决策点附近的锚系统性滞后。DOT 那单的「第二腿高点 1.576」不在 major 里、H2 一度误杀，就是这个滞后 + 窗口太小的组合造成的——你们已经把 H2 改成大小级别合并，是对的，但根因还在。

修法：`swing_window_major` 提到 8–12；`trend_state` 至少用 3 个高点 + 3 个低点并检查序列顺序（HH 必须晚于 HL），或者干脆加一个「近段子窗标签」（你们 changelog 里已记为已知限制）。

## 4. 一句话判断

这套系统的瓶颈不在「看得准不准」，在「拦得住拦不住」。感知层已经把能算的都算了，知识层口径也收得够紧，但裁决层有两条红线实际是松的（RR 按末级目标算、风险放到 1.5%），还有两条是死的（H6 没接线、整数位对小数价失效）。**这四条不修，后面所有回放结论都不可信**——不是方向错，是分母错。

顺带说一句：`ds23` 亏 −1.03R 不用当回事，`DOT` 赚 +2.93R 也不用高兴，n=2 什么也证明不了。真正该盯的是修完 P0 之后，30 段金标准集的通过率会不会掉——如果掉了，说明之前的「通过」是门槛太松换来的。

## 6. 两项裁定的执行（2026-10-30 17:00，用户授权「这两个你来定」）

### 6.1 尝试计数器：不改语义，补「腿数」字段

先查清事实再决定：

- `count_entry_attempts` **只被基线用**（`eval/baselines.py`），判断层与裁决层都不用它——改它不影响金标准、不影响裁决。
- A1 卡写着「回踩已走出第二腿（**腿数由特征包计**）」，但特征包里**根本没有腿数字段**。所以真正的缺陷不是「计数器偏严」，是「卡片依赖的测量压根没做」。

决定：
1. **保留 `count_entry_attempts` 原语义**，在 docstring 里把话说死：它数的是「扩张型尝试」（必须先创新低再反抽），所以「更高的第二腿低点」在它这儿只算 1 次——这是定义，不是 bug。
2. **新增 `pullback.legs` / `pullback.two_legs`**（`perception.legs.count_pullback_legs`）：按 minor 摆动的结构计腿，不看根数，**不设幅度门槛**——多一个拍出来的常数就多一个没人能辩护的自由度（1% 的教训）。

实测（dev 31 段）：腿数分布 1×21 / 2×9 / 4×1 → **两腿以上 10/31（32%）**；对照 `attempts≥2` 只有 2/31（6%）。差的这 8 段正是「第二腿是更高低点」那一类，与卡片「数腿看结构不看根数」的常见误判条目吻合。

### 6.2 P2-9（swing_window_major=5 + 2H/2L）：不动
