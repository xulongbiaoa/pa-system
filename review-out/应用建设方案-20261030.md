# 通用大模型 API 驱动的价格行为自动交易与学习方案

日期：2026-10-30。依据用户本轮明确方向：目标是 AI 自动交易；核心是学到可迁移的价格行为知识、有效复盘进步；使用通用大模型 API，无自有模型；遵守纪律且依据合理的亏损可属预期内，判断失误与违纪须分别识别。

本轮补充目标：AI 必须主动查找支持与反对入场的结构证据，判断是否形成有效共振。重点研究“三推到达大级别阻力与 MM 目标区，二次测试失败后出现触发”的机会。评价证据真实性、相关性与充分性，不以理由字数或条件数量鼓励交易。

本文件新增条件矩阵、候选状态和出场协议均为设计要求，尚未实现于现行 schema、特征包或执行代码。当前知识卡仍是现行交易约束，新组合与出场方法需独立验证和定版。

行情来源与接入方式由用户另行设计，本方案去掉自建行情采集与接入服务；保留外部数据的完整性、收盘时间和决策可见性校验。

具体工程架构见 [自动交易与学习系统架构 v1](../design/自动交易与学习系统架构-v1.md)。该文档细化模块职责、进程部署、数据契约与数据库表、调用时序、订单/持仓状态机、Gold 工厂、控制 API、故障恢复和实施验收。本文保留产品与学习方法；工程实现按架构文档中的接口与状态约束推进。

## 一、什么叫“学会”

普通 API 请求不更新模型权重，也不默认保留之前的交易记忆。本项目的学习载体是外部系统：版本化规则、审定案例、可检索经验、确定性特征、决策记录与独立评估。API 模型负责在给定上下文内推理。

“学会”的验收不是能复述规则、拟合 gold 或解释过去的走势，而是在未见过的行情中：能指出当时可观察的证据；正确区分符合条件与仅外形相似的 setup；写出可验证的失效条件；在冻结测试上减少判断与纪律错误，并在足够的真实成本样本上检验表现。

持续改进包括三种不同变化，必须分别记录：知识表述更准确；提示和案例检索让模型更稳定地执行已有规则；确定性代码纠正感知或风控缺陷。均不宣称为模型权重已经训练。后续若 API 提供合适的微调能力，再独立评估其必要性。

## 二、教学材料如何组织

### 规则层：可操作的知识

每条规则保存：适用语境、前置条件、结构锚点、触发、失效条件、例外边界、证据来源和版本。明确“本系统交易纪律”与“待验证的市场假设”。禁止把未验证倾向包装成市场定律。

沿用 knowledge/core.md、setups/ 和确定性 perception。修复两腿、CLV、毛/净 RR、信号根与决策根等口径差异后再用作教学。

### 案例层：解释为什么成立或不成立

案例至少包括决策点、当时可见 K 线、结构与证据引用、候选条件逐项检查、主备假设、计划、失效条件和审定意见。结果单独保存，不在盲判阶段暴露。

成对选择相似形态：位置合格/不合格、第一腿/第二腿、真突破证据充分/不足、可交易/费用吃掉空间。也必须包含正确决策亏损与错误决策盈利，避免教会模型以结果解释规则。

改变单一关键条件的合成对照可测试规则理解，但合成案例不能当作真实收益样本。

案例应覆盖“结构相似但背景不同”：趋势内三推回调与成熟趋势末端三推，不能仅凭形状作同一解释。三推、二次测试、二次入场分别标注；测试次数不等于入场触发次数，三推也不自动构成 C1 主要趋势反转。首次反向运动只支持回调还是足以支持趋势反转，必须分别举证。

### 经验层：有边界的纠错记忆

每条经验记录错误类型、当时证据、可复现的失败原因、改进假设、适用范围、验证样本与状态。复盘草稿先进入待验证池，未通过评估不得进入生产提示或自动改风控。

检索优先按 setup、结构阶段、位置和不确定因素匹配，补入相似反例；不能只按趋势标签取固定几条。严格排除当前样本及重叠窗口，开发、验证与测试的使用范围必须独立控制。

## 三、AI 如何做一次交易决策

已收盘行情 → 截止决策点的结构特征 → 相关规则与正反案例 → API 结构化判断 → 契约与证据校验 → 确定性风险裁决 → 自动执行 → 持仓与结果记录。

AI 输出主假设、备选假设、证据引用、setup 条件检查、候选计划或空仓原因。每个关键判断必须指向具体字段/根号/价位；事实不足时允许明确未定。不能以模型自报信心替代证据。

代码验证引用是否存在、来源是否在决策时刻可见、价格与订单方向是否合法，以及风险、费用、账户和交易所约束。AI 不直接跳过裁决调用下单权限。

每次决策存档输入数据边界、特征版本、知识与提示版本、模型标识、完整请求与响应、校验和裁决结果。历史摆动必须记录确认时刻，不能把之后才确认的极值提前画成当时已知结构。

初期用收盘事件驱动分析，避免每个价格跳动都调用模型。已挂订单或持仓的常规保护由代码持续运行，不等待模型回复。新决策与已有订单、仓位必须统一处理，防止重复入场。

### 3.1 多因素证据链

读图顺序沿用 core：缺口账本 → 语境与双方目标 → 预画关键位置 → setup 触发 → 形态校验。下表是组织判断与校验的维度，不以“三推形状”替代背景审计。

| 维度 | 必须回答的问题 | 证据要求 |
|---|---|---|
| 背景 | 顺势、区间还是潜在反转？大级别是否支持本方向？ | 周期、已收盘结构、缺口与目标状态；分别保存感知标签和 AI 判断语境 |
| 位置 | 为什么在这里观察？ | 预画阻力/支撑带的边界、来源与确认时间，MM 的测量腿、投影起点和目标 |
| 接近过程 | 价格怎样到达该位置？ | 三推各自起止锚点、推进幅度、回撤、重叠与跟进；允许“无衰竭”结论 |
| 测试行为 | 哪次尝试失败？ | 第一次测试、离开该区域、第二次测试的时间与价位；不是相邻两根 K 线就算两次测试 |
| 触发 | 为什么现在可以执行？ | 已收盘信号、收回/突破的具体沿口、所需跟进和信号有效期 |
| 反证 | 什么支持相反判断？ | 突破被接受、方向性跟进、结构仍推进等实际观测；没有查到不等于已证明不存在 |
| 风险与空间 | 错在哪里退出，最近合理目标能否覆盖风险和成本？ | 结构外止损、前提线、首目标、费用与执行偏差；等待确认后按当下价格重新核算 |

每条证据建议记录：evidence_id、claim、role、status、timeframe、bar_refs、price_refs、feature_refs、available_at、rule_version、dependency_group。status 为满足/不满足/未定/不适用；role 为必需/增强/否决。观测事实与对事实的推断分开，无法通过现有特征包确认的关键证据标未定，进入特征补齐流程，不能只凭自由文字放行。

dependency_group 用于识别同源证据：前高、区间上沿和阻力若来自同一高点，不视为三个独立确认；MM 使用相同锚点时也要记录依赖。此处不假设统计独立，不把满足项数换成胜率。

### 3.2 条件组合与反证优先

每个 setup 版本预先定义必需条件、增强证据、否决条件及其组合关系，不能让 AI 看到行情后临时降低要求。入场要求所有必需项满足、没有已触发的否决项且关键否决检查无未定；增强项不能抵消必需项缺失或风险违规。不同 setup 使用不同组合，不要求所有交易都同时具备三推、MM 和二次测试。

“三推 + 大级别阻力 + MM + 二次测试失败”的研究组合，应先记录客观锚点、再审失败证据，最后检查触发与 RR。重合区宽度、有效测试的离开距离、失败确认方式、信号有效期都要在样本协议中定版；本方案不随意补数值阈值。还未定版时只能作研究候选。

该组合不能直接映射成现有 C1：仍须满足 C1 已规定的趋势年龄、衰竭尝试与趋势线破坏/回测要求；若属于突破失败，则须满足 B3 的突破与回收窗口。无法对应现行卡的组合单独立项评估，不能借用某个 setup 名称绕过前置条件。

大级别只使用决策时已收盘的数据；低周期不能凭空推断缺失的大级别历史。大级别摆动的确认时间、MM 锚点的选用时间必须可追溯，禁止目标到达后重新挑测量腿。

### 3.3 等待也是结构化输出

候选状态建议为：观察 → 等待测试/触发 → 可执行，或失效/过期。状态随新事实变化，但每次保留快照；可执行之后由订单状态机接管。

示例（假设场景，不代表现成交易信号）：阻力、MM 到达与三推已有证据，二次测试尚未失败，则输出等待；如果后续失败与触发得到确认，重新核算当下入场空间；若突破获得接受则取消反转假设；若确认太晚造成 RR 不足也放弃。不能为了凑条件提前使用下一根 K 线，不能用已经错过的触发价美化计划。

每个判断最终回答：为什么是这里、为什么是现在、最强反证是什么、还缺什么、什么事实导致取消/退出。空仓需要说明缺失或否决项，不能用模糊的“位置不好”替代检查。

### 3.4 出场证据与优先级

| 出场类型 | 执行原则 |
|---|---|
| 硬止损及账户保护 | 独立触发，不等待额外证据或 API 回复 |
| 交易前提失效 | 按入场前写定的可计算条件执行；与硬止损不是同一条线 |
| 固定目标与到期 | 沿用已批准的目标/生命周期规则，不因等待额外确认而跳过 |
| 多因素主动止盈 | 新策略版本的研究项；预先定义目标区域、衰竭/反向测试条件及执行方式后评估 |

例如“多单到达预画的对侧阻力与 MM 区域，第二次上攻失败后退出”可作为出场实验。必须与原固定目标方案对照，比较额外确认导致的盈利回吐与提前退出成本。当前 core 禁止持仓中改近目标，因此该实验在定版前不改变生产出场，不能把它伪装为临时前提失效。

同根触发多种退出时预先定义优先级；OHLC 无法判断先后时沿用保守约定，不能挑更盈利的路径。入场研究与出场研究分开比较，再评估组合效果，避免无法识别改进来自哪里。

## 四、复盘：先审决策质量，再看盈亏

### 第一步：冻结原决策

保留交易前证据、计划和规则版本，不能事后补理由。原判断不覆盖，修订意见另存。

### 第二步：隐藏结果进行重审

评审输入只包括当时可见的信息与当时规则；先独立重建判断，再与原决策比较。检查语境、位置、触发、目标、失效条件和不确定性，不以未来涨跌裁定对错。

同一个通用模型的自评可能重复原有偏见。确定性检查优先，关键争议进入人工裁定；可选另一模型交叉评审，但“多模型一致”仍不是事实证明。审计可用结构化理由和证据，不依赖获取模型内部思维过程。

### 第三步：核对执行事实

对比已批准计划与实际订单、成交、滑点、撤单、保护单和退出。区分模型提出违纪计划、代码错误放行、执行器偏离计划。计划在成交前被 gate 拒绝也需要复盘，不能只复盘已成交交易。

### 第四步：单独查看结果

| 决策与纪律 | 盈利 | 亏损 |
|---|---|---|
| 证据合理、纪律合规 | 保留为合规盈利样本 | 可能是预期内结果，不因单笔亏损改规则 |
| 判断失误或违纪 | 仍计为错误，不能奖励错误行为 | 按证据和执行链定位问题 |

遵守纪律是必要条件，不足以证明判断正确；判断合理也不保证现行策略具有优势。单笔无法判定“正常方差”或策略失效，累计分布偏离预期时另行检验。

### 第五步：归因与动作

- 感知错误：特征/时间边界/结构锚点错误 → 修代码并补针对性回归。
- 判断错误：当时已有反证被忽略、把第一腿当第二腿、目标序列错误 → 补有证据的反例或修改提示，评估后晋升。
- 纪律与裁决错误：计划违背规则、违规被放行 → 明确违规来源并修校验/风控。
- 执行错误：订单、保护、仓位或退出与批准计划不一致 → 修执行链与恢复机制。
- 暂未发现错误：保留结果并累计观察，不用“止损了”证明判断错，也不用“按计划退出”证明判断对。
- 证据不足/争议：暂不定论，不写入已确认的教学知识。

允许一笔交易有多个问题，避免只用一个类别掩盖因果链。当前 judge/reflect.py 的规则化初分不足：正常止损/止盈就归方差、到期就归执行偏差，必须改为上述基于证据的审计流程。

复盘逐项核对证据矩阵：事实是否真实、当时是否可见、是否重复计数、推断是否成立、反证是否遗漏、触发是否过早/过晚。错误应定位到证据 ID 和规则版本；正确亏损保留其有效证据，错误盈利仍保留错误标记。事后重审新增的解释不得回填为原决策已知依据。

## 五、怎样证明系统进步

每轮只提出一个可检查的改进，例如“减少第一腿误判为第二腿”，而非笼统追求更高胜率。

流程：失败样本提出假设 → 开发集建立对照 → 冻结旧版和新版 → 验证集比较 → 达到预先约定条件才发布 → 独立留出集审计。测试集一旦反复用于选版本，就不再是独立留出，需要滚动增加新的未见时间段。

隔离同一行情的重叠决策窗口与未来结局窗口，时间边界须留出足够间隔；同一交易机会不能拆成几十个“独立”成功样本。检索库也遵守数据隔离。

评估分三层，不压成一个总分：

1. 知识与判断：关键事实错误率、证据可追溯率、setup 前置检查、失效条件完整性、相似反例辨别、重复判断稳定性。
2. 纪律与系统：违规提案率、违规放行率、重复订单、无保护仓位、状态恢复正确性。
3. 交易结果：净 R、回撤、成本、未成交、持仓时间及分 setup/周期表现，记录样本量和不确定性。市场效果必须用真实行情验证。

Gold 28/30 为空仓，永远空仓就有 93.33% 一致率。必须分别看候选召回、误报、理由质量；空仓样本也抽查是否错过合法机会，防止只审已交易样本。

增加条件采用消融对照：固定基础候选机会集合，分别去掉三推、位置重合、二次测试等增强项，比较事实错误、误报、漏报、信号数、确认延迟、入场 RR 和净结果。硬风控不参与放宽实验。不同版本按各自真实触发时间成交；未触发也留档，不能只比较两边都成交的样本。完整序列还需分别回放订单/持仓冲突，不能把事件级对照当成完整组合绩效。

不奖励“证据越多越好”，优先考核有依据的必需项覆盖、事实正确性、反证处理和空仓解释；额外条件若只改善开发集、显著压缩样本或造成过晚入场，不应直接晋升。每轮预先冻结比较方案，避免反复挑条件直到回测漂亮。

模型或 API 版本变化应重新跑同一评估；记录服务端返回的模型标识和参数，不能假设不同时间的 API 输出完全可复现。

## 六、自动交易闭环

沿用 Python 核心，消费用户另行提供的行情数据，增加 API 判断适配器、决策调度、订单执行、持仓状态机、持久化事件记录与复核评估任务。先采用单体服务，避免提前拆微服务。界面以监控、审计、暂停和查看证据为主。

工程形态定为模块化单体、同仓库同镜像下的四类进程：api、decision-worker、execution、learning-worker。模型判断和离线学习不持有交易权限，execution 是唯一账户交易写入口。采用 PostgreSQL 存状态、风险预占和持久任务，内容寻址文件卷存不可变快照与模型记录；小规模案例先按结构字段检索。在线读取已发布 ReleaseBundle，离线学习只产候选版本，发布后才影响新决策，已有仓位仍使用原退出版本。

架构第 3 节列出当前模块的复用/新增边界，第 4–6 节定义证据、判断、订单授权和执行状态，第 7–9 节定义 Gold/复盘/发布流水线、表结构和控制 API，第 11–12 节给出故障验收与分阶段交付。

订单必须有持久化业务标识和幂等键。下单超时先查询状态再决定重试；处理部分成交、撤单/成交竞态、精度与最小数量。重启时从交易所重建订单/仓位事实并与本地事件对账，未对齐时停止新开仓。

持仓管理实现固定止损/目标、结构化前提失效退出及到期退出。已成交仓位立即确认保护，保护失败时停止扩仓并按预定退出策略处理。暂停新开仓和紧急平仓是不同操作，既有保护不能随分析任务暂停而消失。

模型超时、格式错误、证据不足或行情陈旧：不产生新订单；已有仓位仍受确定性保护管理。配置账户总风险、单标的风险、并发仓位与亏损停机条件，明确这些约束与策略判断的分工。

交易所、现货/合约、标的、周期、资金上限和实盘启用条件尚未确定；后续执行设计须落实这些输入。此次文档与 Git 提交不代表授权真实账户交易。

## 七、落地顺序和验收

### M0：教学与规则可信

修正 gold 的确定事实错误，裁定 DOT/ds23 等争议，保留原件另立修订版本；修复自样本召回；统一两腿、CLV、净 RR 与失效条件。验收：每个候选可追溯前置条件与结构锚点，冻结集用于回归，另有隔离的评估数据。

第一轮建议抽取 20 个独立事件，其中 10–15 个同一结构族事件做深度标注，其余加入其他结构或随机决策点作对照；覆盖完整组合、缺触发、反证成立、确认后空间不足，以及审定后揭示的合理亏损和错误盈利。该数量只验证标注流程，不证明策略优势；历史集缺大级别数据时先补齐时间对齐的原始行情。

Gold 生产按“代码准备考题包 → 两份独立模型标注 → 事实核验 → 人工裁定及一致答案抽查 → 冻结决策后揭示结果 → 版本发布”执行。对同一事件逐阶段保存等待、触发或取消快照，标出促使动作改变的新增证据；整组隔离，不能把快照当独立交易扩充样本。事实核验、决策审定与结果复现分别记状态，模型一致或交易盈利均不能替代审定。具体流程、交付物和批次验收见同目录《gold复核-20261030.md》“证据型 Gold 建设协议”第 5–7 节。

### M1：可评估的 API 决策

接通结构化模型判断、输入快照和裁决，建立隐藏结果的评审及成对案例测试。验收：能完整处理合格、拒绝、空仓、无效响应与超时；可比较两个版本的具体错误，不能靠记住 gold 通过。

补齐契约对必需/增强/否决、证据来源、等待条件和候选有效期的表达。增加校验场景：同源理由重复、未收盘大级别、三推但无反转触发、二次测试尚未完成、硬否决被增强证据抵消；这些场景不得被模型自由文字绕过。

### M2：自动模拟交易与复盘

同一决策链驱动历史回放、实时影子运行与模拟执行；接通订单/仓位状态机、成本和失效退出；复盘先盲审后核对执行与结果。验收：不看未来、不重复订单、可恢复、违规盈利仍记错、合规亏损不自动改规。

### M3：受控发布与持续学习

达到预先约定的决策、风控、执行和统计门槛后，按用户明确的账户与风险范围启用有限实盘。改进提案先离线验证，再影子比较，最后发布并保留回滚版本。生产复盘不直接热改规则，不把单笔结果自动奖励给系统。

核心产物是一个“可审计、能验证改进、能执行交易”的系统。复盘笔记数量、模型措辞自信程度和漂亮的单次回测均不作为学会的证明。

## 八、价格行为概念来源与适用边界

Brooks 的三推反转材料将三推后的反转 setup 与触发区分开；三推回调材料又将趋势内回调置于不同语境。这里采用其“形态需要结合背景与触发解释”的概念框架，不引入教材中的胜率或收益断言作为本系统先验。参见 [Wedges and Other Three-Push Reversal Patterns](https://onlinelibrary.wiley.com/doi/abs/10.1002/9781119202622.ch5) 与 [Wedge and Other Three-Push Pullbacks](https://onlinelibrary.wiley.com/doi/10.1002/9781119202608.ch18)。

证据矩阵、同源去重、等待状态、gold 晋升及消融评估为本项目设计。用户提出的多因素组合仍需本市场、本周期、本成本口径下的独立验证；原书概念不能代替系统实测。
